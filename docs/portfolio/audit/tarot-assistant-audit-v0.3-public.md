# 塔罗助手项目审计文档 v0.3

## 1. 审计对象和范围

本次审计对象为塔罗咨询场景中的 AI 产品原型，公开实现与演示以本仓库和 Render 部署版本为参考。

本公开版本仅保留可对外展示的产品审计结论；内部工作底稿、原始案例和私密资料不随仓库发布。

本次审计重点不是判断项目是否已经商业化成熟，而是判断它作为一个 AI 产品经理求职项目，目前已经完成了什么、缺口在哪里、哪些问题应先处理、哪些内容可以沉淀为后续 PRD 和作品集材料。

## 2. 项目一句话定位

塔罗助手是一款面向塔罗占卜咨询场景的 AI 辅助工具，目标是将提问、事件分类、牌阵选择、抽牌、牌意解读、反馈微调、结果归档和历史浏览等原本依赖人工经验且重复度较高的工作流程，转化为结构化、可复用、可沉淀的 AI 辅助流程。

它对 To C 客人的核心价值是：围绕用户自己的问题生成个性化内容，解释牌面与事件之间的关系，提供情绪价值、建议参考和完整叙事，让客人感受到这次占卜是围绕自己的具体问题展开，而不是收到一段通用牌意说明。

它对你作为产品负责人和实际使用者的核心价值是：减少重复解释、重复整理、重复归档和重复调整话术的工作，提高塔罗咨询流程的效率，并把经验沉淀为可管理、可评估、可迭代的产品系统。

## 3. 目标用户

### 3.1 核心用户：To C 客人

核心用户是来进行塔罗占卜咨询的客人。

他们的核心需求包括：

- 围绕自己的问题获得个性化解读。
- 理解抽到的牌和问题之间的关系。
- 在内容中获得被理解、被回应和被安抚的感觉。
- 获得针对事件本身的建议参考。
- 感受到这次咨询内容完整、有信息量、有价值。

### 3.2 次要用户：产品负责人和咨询工作流使用者

次要用户是你自己，也就是需要按照 To B 环节优化工作效率的人。

你的核心需求包括：

- 减少重复性的解读劳动。
- 让咨询流程形成稳定 SOP。
- 管理客户档案和历史记录。
- 按事件分类沉淀案例。
- 根据反馈快速调整生成结果。
- 减少每次咨询从零组织话术的成本。
- 在后续迭代中逐步形成评测表、数据记录和复盘材料。

这里需要注意：产品面向客人提供内容价值，但实际管理端服务的是你的工作效率。后续 PRD 需要分别写清楚客人端目标和管理端目标，不能混在一起。

## 4. 完整用户流程

以下流程节点以产品负责人确认过的文字转录为唯一事实来源。后续 PRD、评测表和代码改动说明涉及流程时，必须逐字引用节点名称，不得改写、合并、拆分或自行补全。

### 4.1 全局注释

历史浏览是全局入口：主流程任意步骤均可进入（图中虚线便签，不单独画连线）。

### 4.2 访客端流程

A1. 用户端进入操作主界面（起止框）

A2. 主界面 → 进入历史界面

A3. 主界面 → 判断：是否输入问题

否 → 不输入问题 → 选择事件分类

是 → 输入问题 → 选择事件分类

A4. 选择事件分类 → 选择牌阵

A5. 选择牌阵 → 牌阵分类（共13类，逐字如下）：单张牌、维纳斯爱之牌阵、双抉择牌阵、二选一牌阵、凯尔特十字、质点牌阵、无意识之山、画像牌阵、时间线分支、宠物牌阵、四季牌阵、万能牌阵、时间流运势牌阵

A6. 选择牌阵 → 判断：虚拟/实体牌

实体牌 → 下拉框选择牌（搜索牌名）→ 点击设置正逆位 → 已选牌面界面显示牌面

虚拟抽牌 → 点击开始虚拟抽牌 → 载入抽牌界面（显示牌阵样式，未选牌阵显示透明框）→ 选择抽N张牌（可左右翻页选择）→ 显示已抽牌面及数量（已抽x/y张）→ 点击确认开始占卜 → 已选牌面界面显示牌面

A7. 抽牌过程三个侧操作：退回重抽抽取的最后一张（回到"选择抽N张牌"）；重置全部（全部重抽）；取消（返回主界面，保留已抽牌阵和牌面）

A8. 已选牌面界面显示牌面 → 判断：是否是万能牌阵及时间流牌阵

否 → 生成解读

是 → 判断：是否填写问题

是 → 生成解读

否 → 提示需要填写问题 → 确定 → 返回主界面补充问题

A9. 生成解读 → 生成文本过程中显示加载提示词 → 输出解读内容

A10. 输出解读内容 → 三个分支：

重新开始 → 返回主界面

生成反馈栏填写反馈 → 根据反馈修改 → 反馈栏删除修改内容 → 回到输出解读内容

保存到历史 → 保存历史提示 → 关闭网页（结束）/ 确定 → 返回主界面

### 4.3 访客端·历史浏览分支

B1. 进入历史界面 → 浏览历史（默认展示全部事件卡牌、分类）

B2. 浏览历史 → 事件分类筛选 → 全部 / 综合运势 / 恋爱 / 事业 / 学业 / 人际关系 → 事件卡片 → 展开解读 / 编辑分类 / 删除

B3. 浏览历史 → 事件查询（待加功能，未实现）

B4. 进入历史界面 → 返回主界面

### 4.4 管理端流程

管理端流程与访客端相同的部分不再重复，以下为先导差异段。

C1. 输入管理密码 → 进入 → 管理端进入界面（起止框）

C2. 管理端进入界面 → 四个功能分支：

档案分流 → 不创建直接跳过 / 创建客户背景 → 进入操作主界面

注释：匿名路径（不创建直接跳过）不保存历史，用于一次性快速占卜，属于有意设计。

导出记录

导入记录

退出 → 回到输入管理密码

C3. 管理端进入界面 → 进入历史界面（结构与访客端 B1-B4 完全一致；返回主界面回到"管理端进入界面"）

C4. 进入操作主界面 → 判断：是否输入问题

否 → 不输入问题 → 选择事件分类

是 → 输入问题（提问包含引导词）→ 选择事件分类

C5. 之后流程与访客端 A4-A10 一致（选择牌阵 → 牌阵分类13类 → 实体牌/虚拟抽牌 → 生成解读 → 输出解读内容 → 重新开始/反馈链/保存到历史）

## 6. 功能范围：需求卡片

本节将 v0.2 中已经确认的功能范围改写为需求卡片。每张卡必须包含六个要素：是什么、为什么、怎么做、做到什么程度、优先级、进哪个版本。任何一项缺失，都不能进入开发排期。

需求卡片的“是什么”同时写明本次改动范围和明确不做什么；“为什么”必须对应第 3 节已经确认的用户痛点；“怎么做”同时写明方案、界面位置和用户操作流程；“做到什么程度”必须能通过走查、数据或评测表验证。

### 6.1 P0：按访客端流程节点 A1-A10 分组

#### A1. 用户端进入操作主界面

##### P0-A1-01 新手引导和首页信息层级

- **是什么**：在用户端进入操作主界面增加首次使用说明、核心价值说明、流程入口和下一步行动区；改动范围包括首页信息层级、说明文案和首次进入状态。**不做什么**：不新增账号注册、支付、会员体系，不改变核心抽牌和生成接口。
- **为什么**：对应第 3 节核心用户“需要围绕自己的问题获得个性化解读”“需要感受到内容完整、有价值”，也对应第 3 节次要用户“让咨询流程形成稳定 SOP”。
- **怎么做**：在用户端主界面顶部放置一句话定位和首次使用说明，在问题输入区之前增加流程入口说明，在页面中按“提问→分类→牌阵→抽牌→解读→保存”显示步骤提示；首次进入显示引导，关闭后不重复遮挡主流程。
- **做到什么程度**：首次进入主界面能看到说明和开始入口；关闭引导后可以直接进入问题输入；刷新页面不会重复弹出已关闭的引导；桌面端和手机端均不出现遮挡或横向溢出。
- **优先级**：P0；前置依赖为现有访客端主界面和 A3 问题输入区域。
- **进哪个版本**：v1.1。

##### P0-A1-02 首页入口和状态保持

- **是什么**：整理首页的主操作入口、历史入口、当前牌阵状态和重新开始入口。**不做什么**：不重写历史数据结构，不改变匿名访问路径。
- **为什么**：对应第 3 节核心用户需要“不被复杂操作打断”，以及次要用户需要减少重复整理和返回操作。
- **怎么做**：将“开始一次占卜”“进入历史”“重新开始”区分为明确入口；当用户从抽牌或解读页面返回时，保留已选牌阵和牌面状态，只有点击重新开始才清空本次流程。
- **做到什么程度**：从主界面进入历史、从历史返回主界面、从抽牌取消返回主界面、从解读重新开始均能回到预期页面；当前问题、分类、牌阵和牌面不因普通返回而意外丢失。
- **优先级**：P0；前置依赖为现有页面状态管理。
- **进哪个版本**：v1.1。

#### A2. 主界面进入历史界面

##### P0-A2-01 历史入口和返回路径

- **是什么**：优化主界面到历史界面的入口、历史页标题、返回主界面入口和当前记录数量展示。**不做什么**：不在 P0 实现事件查询，事件查询仍按 v0.2 记录为待加功能。
- **为什么**：对应第 3 节核心用户需要保存和回顾历史记录，也对应次要用户需要管理客户和历史记录。
- **怎么做**：在主界面提供稳定的历史入口；历史页显示全部记录、分类筛选和返回入口；访客端继续使用浏览器本地历史，管理端继续使用已有客户档案历史。
- **做到什么程度**：点击历史入口能进入历史页；点击返回能回到正确的主界面；历史记录为空时显示空状态；历史记录存在时显示记录数量和分类状态；不同端不会跳错路由。
- **优先级**：P0；前置依赖为现有历史记录组件和端内路由状态。
- **进哪个版本**：v1.1。

#### A3. 主界面判断是否输入问题

##### P0-A3-01 问题输入和提问引导

- **是什么**：优化问题输入框、不同牌阵对应的引导词、空问题状态和提交前提示。**不做什么**：不改变“万能牌阵和时间流牌阵需要问题”的既有业务规则，不替用户自动编造问题。
- **为什么**：对应第 3 节核心用户需要内容围绕自己的问题展开，也对应 AI 输出结构中的“对事件的基本推断、定义、理解”。
- **怎么做**：根据牌阵显示对应提问提示；输入框附近说明什么样的问题更容易得到具体解读；用户点击开始时检查必填规则；非必填牌阵允许空问题，但不把空问题评价为用户没有想清楚。
- **做到什么程度**：万能牌阵和时间流牌阵空问题不能进入生成；提示文字明确指出需要补充什么；普通牌阵空问题可以按牌阵位置生成；提交后问题内容能进入生成上下文和历史记录。
- **优先级**：P0；前置依赖为现有问题输入、牌阵状态和生成前校验。
- **进哪个版本**：v1.1。

#### A4. 选择事件分类

##### P0-A4-01 事件分类选择和自动分类提示

- **是什么**：优化事件分类选择区、当前分类反馈和问题自动分类后的可修改入口。**不做什么**：不在 P0 扩展新的分类，不改变已有“综合运势、恋爱、事业、学业、人际关系”分类语义。
- **为什么**：对应第 3 节核心用户需要内容与自己的问题直接相关，也对应次要用户需要按事件分类沉淀案例。
- **怎么做**：问题输入后给出自动分类结果；用户可以手动修改；分类结果在生成前、历史卡片和管理端记录中保持一致；“恋爱”仅指浪漫关系，“人际关系”覆盖其他关系。
- **做到什么程度**：输入典型问题后出现分类结果；用户可在生成前修改；修改后的分类被保存；历史筛选和管理端显示与最终选择一致。
- **优先级**：P0；前置依赖为现有分类常量、自动分类函数和历史数据字段。
- **进哪个版本**：v1.1。

#### A5. 选择牌阵

##### P0-A5-01 牌阵比较和选择说明

- **是什么**：优化 13 类牌阵的展示、比较、适用场景说明和选中状态。**不做什么**：不新增牌阵，不改变已有 13 类牌阵名称、牌位含义和双抉择牌阵 18 张牌规则。
- **为什么**：对应第 3 节核心用户需要容易理解的抽牌流程和清晰牌阵展示，也对应次要用户需要将咨询 SOP 固定下来。
- **怎么做**：按使用目的、问题类型和牌张数量展示牌阵卡片；提供简短适用说明；选中后显示牌阵名称、牌位数量和下一步抽牌入口；移动端采用可滚动或分组布局。
- **做到什么程度**：13 类牌阵均可被找到、选中和取消；每个牌阵显示适用说明；选中牌阵后牌张数量和位置说明正确；双抉择牌阵实际抽牌数量保持 18 张，牌位和布局一致。
- **优先级**：P0；前置依赖为现有 SPREADS、牌阵图片和牌阵布局配置。
- **进哪个版本**：v1.1。

#### A6. 选择虚拟牌或实体牌

##### P0-A6-01 抽牌方式选择和已选牌阵展示

- **是什么**：优化实体牌选择、虚拟抽牌入口、牌阵样式展示和已选牌面反馈。**不做什么**：不改变实体牌和虚拟抽牌两种模式，不把真实牌图上传公开仓库。
- **为什么**：对应第 3 节核心用户需要清晰查看牌阵和牌面，也对应次要用户需要减少重复选牌和记录工作。
- **怎么做**：选择牌阵后先选择虚拟或实体模式；虚拟抽牌页显示牌阵样式和透明位置框；实体牌页显示牌名搜索、正逆位设置和已选牌位；两种模式完成后统一回到已选牌面界面。
- **做到什么程度**：用户可以明确知道当前抽牌模式；虚拟模式显示已抽 x/y 张；实体模式能搜索牌名并设置正逆位；完成后已选牌面与牌阵位置一一对应；桌面端和手机端不重叠。
- **优先级**：P0；前置依赖为现有 VirtualDraw、CardSelector 和 SPREAD_CARD_POSITIONS。
- **进哪个版本**：v1.1。

#### A7. 抽牌过程侧操作

##### P0-A7-01 抽牌过程中的回退、重置和取消

- **是什么**：统一抽牌过程中“退回重抽最后一张”“重置全部”“取消”三个侧操作的按钮位置、状态和返回逻辑。**不做什么**：不改变抽牌随机性和牌面数据结构。
- **为什么**：对应第 3 节核心用户需要不被复杂操作打断，也对应次要用户需要减少重复操作成本。
- **怎么做**：在抽牌界面固定显示三个操作；退回只撤销最后一张，重置清空全部，取消返回主界面并保留已抽牌阵和牌面；操作后更新已抽数量和牌阵展示。
- **做到什么程度**：三种操作的结果互不混淆；退回不会删除前面已确认的牌；重置后数量归零；取消后返回路径正确；点击过程中不会重复提交或出现空白页。
- **优先级**：P0；前置依赖为 VirtualDraw 状态和牌阵位置映射。
- **进哪个版本**：v1.1。

#### A8. 已选牌面和生成前判断

##### P0-A8-01 已选牌面确认和必填规则提示

- **是什么**：优化已选牌面界面、牌位对应关系、生成入口和万能牌阵/时间流牌阵的必填提示。**不做什么**：不改变万能牌阵和时间流牌阵必须填写问题的规则。
- **为什么**：对应第 3 节核心用户需要看到当前占卜过程和清晰牌阵，也对应 AI 输出质量中的问题相关性和牌阵位置对应。
- **怎么做**：生成前展示牌阵名称、每个牌位、牌名和正逆位；对必填问题做阻断提示；用户确认后进入生成；点击确定后返回主界面补充问题。
- **做到什么程度**：所有已选牌位均有对应牌面；缺问题时不能生成；提示明确指出补充位置；补充后能继续生成；其他牌阵不被错误阻断。
- **优先级**：P0；前置依赖为问题字段、牌阵 slots 和 cards 状态。
- **进哪个版本**：v1.1。

#### A9. 生成解读和生成状态

##### P0-A9-01 生成过程状态、错误和重试

- **是什么**：优化生成解读页面的加载提示、流式输出状态、异常提示和重新生成入口。**不做什么**：不在 P0 更换模型供应商，不处理已经通过切换工作流规避的外部 API 通道问题。
- **为什么**：对应第 3 节核心用户需要清楚知道当前占卜过程，也对应次要用户需要减少生成失败后的重复处理。
- **怎么做**：生成前显示准备状态，流式输出时显示进行中状态，完成后显示结果；请求失败时显示可理解的错误和重新生成入口；保留已选问题、分类、牌阵和牌面。
- **做到什么程度**：点击生成后出现状态反馈；流式文本能持续显示；完成后进入完整输出；失败时不出现空白页，用户可以重试；生成状态不会与旧结果混淆。
- **优先级**：P0；前置依赖为 SSE 读取、前端 loading 状态和现有 `/api/generate-public`、`/api/generate`。
- **进哪个版本**：v1.1。

#### A10. 输出解读、反馈、总结和归档

##### P0-A10-01 解读内容阅读结构

- **是什么**：优化解读页面的内容层级、牌位标题、逐牌内容、总结、建议、免责声明和情绪回应的阅读结构。**不做什么**：不改变已确认的 AI 输出模块比例和技术边界，不在 P0 完成自动模型评审。
- **为什么**：对应第 3 节核心用户的核心需求“内容输出、情绪价值和建议参考”。
- **怎么做**：按“招呼引导→事件理解→牌面初判→逐牌解读→三牌总结→事件映射→免责声明→建议→情绪回应”组织页面；提供目录或锚点；长文本分段展示，移动端避免横向溢出。
- **做到什么程度**：输出页面包含可定位的内容模块；每张牌能对应牌位；总结和建议不会被埋在长文本中；免责声明可见；手机端无文字遮挡和按钮重叠。
- **优先级**：P0；前置依赖为当前生成文本格式和输出页面组件。
- **进哪个版本**：v1.1。

##### P0-A10-02 反馈微调、二次生成和归档

- **是什么**：整理“反馈栏填写→根据反馈修改→删除修改内容→重新查看→保存到历史”的操作链。**不做什么**：不把一次反馈自动写入长期知识库，不把单次微调直接认定为模型训练。
- **为什么**：对应第 3 节次要用户需要根据反馈快速调整输出、保存和回顾历史。
- **怎么做**：在输出页提供反馈入口和二次生成按钮；二次生成保留原结果和修改后结果的可区分状态；用户确认后保存到历史；删除反馈内容只删除本次反馈，不影响原始记录。
- **做到什么程度**：反馈提交后能生成修改结果；用户可以重新点击解牌进行二次生成；未确认前不覆盖原始历史；保存后分类、问题、牌阵、牌面和最终文本完整记录。
- **优先级**：P0；前置依赖为现有 reviseOutput、save/archive 逻辑和历史数据结构。
- **进哪个版本**：v1.1。

### 6.2 P1：数据、质量和管理能力，按内部依赖排序

#### P1-01 数据库方案选择

- **怎么做**：比较 MongoDB、其他托管数据库和继续使用文件存储的成本、隐私、备份、迁移和开发难度；确定数据表/集合、备份策略、删除策略和迁移方案。
- **做到什么程度**：形成一页数据库方案决策记录；列出核心数据实体、字段、访问权限、备份和恢复方式；明确 `server/data.json` 的迁移和回滚方案；未完成方案前不改生产数据。
- **优先级**：P1；前置依赖：无，是后续 P1 的基础依赖。
- **进哪个版本**：v1.2。

#### P1-02 基础埋点

- **是什么**：记录核心流程节点的访问、完成、退出、生成成功、生成失败、保存和反馈等基础事件。**不做什么**：不采集聊天原文、客户姓名、完整占卜内容或 API 密钥，不做复杂用户画像。
- **为什么**：对应当前运营问题中“不清楚网站流量、退出位置、生成失败率和保存率”。
- **怎么做**：在 A1-A10 关键节点定义匿名事件名和必要属性；记录时间、流程节点、牌阵类型、分类、结果状态和耗时；隐私字段默认脱敏。
- **做到什么程度**：至少能统计访问次数、生成开始/成功/失败、保存次数、反馈次数和各节点退出；事件字段有文档；埋点数据可被后续看板读取。
- **优先级**：P1；前置依赖：P1-01 数据库方案选择；同时依赖 A1-A10 的节点定义。

#### P1-03 规则自动检查

- **是什么**：在生成完成后对字数、违禁词、Markdown、装饰符号、牌位覆盖、免责声明和边界表达做本地规则检查。**不做什么**：不以规则检查代替内容质量判断，不阻断用户查看主结果。
- **为什么**：对应当前 AI 问题中输出主要依赖 prompt、质量参差不齐、缺少量化标准的问题。
- **怎么做**：根据第 7 节输出结构和第 9 节规则清单建立检查函数；生成结束后异步或快速执行；把通过、风险和失败项写入质量记录。
- **做到什么程度**：规则能输出结构化检查结果；C 端不展示内部评分；出现规则失败时仍能查看结果；管理端或测试模块能查看失败项和原文定位。
- **优先级**：P1；前置依赖：P1-01；排期依赖 P1-02 的基础记录接口；并行依赖为 prompt 版本号。
- **进哪个版本**：v1.2。

#### P1-04 管理端质量记录测试模块 v1

- **是什么**：在管理端增加质量记录和测试模块 v1，查看单次生成的输入摘要、牌阵、规则检查结果、人工评语和评测表结果。**不做什么**：不在 v1 实现自动模型评审，不把质量分数展示给 To C 客人。
- **为什么**：对应当前 AI 评审记录缺失、输出质量依赖个人反馈且迭代没有记录的问题。
- **怎么做**：以生成记录为单位保存评测项；支持查看、标记通过/失败、填写备注、关联 prompt 版本和模型配置；优先支持手动录入和规则结果展示。
- **做到什么程度**：可以打开一条生成记录并看到规则检查、评测表和人工备注；质量记录与原始会话关联；刷新和重新部署不会丢失已保存记录；C 端不可见。

#### P1-05 基础数据看板 v1

- **是什么**：在管理端增加基础数据看板 v1，展示访问、流程完成、生成、失败、保存、反馈和牌阵分类等聚合数据。**不做什么**：不在 v1 做增长归因、广告投放分析、用户画像和付费转化看板。
- **为什么**：对应当前运营问题中缺少流量监测、数据看板和流程漏斗判断。
- **怎么做**：基于 P1-02 埋点展示总访问、生成成功率、失败率、保存率、反馈率、牌阵使用分布和节点退出；支持按时间范围筛选；默认只展示匿名聚合数据。
- **做到什么程度**：看板能读取真实埋点并显示统计；指标口径有文档；空数据时有明确状态；指标可以和原始事件记录抽样核对。
- **优先级**：P1；前置依赖：P1-01、P1-02；功能依赖 P1-04 的质量记录结构可选，不阻塞基础流量指标。

- **是什么**：主生成完成后异步调用评审模型，对问题相关性、解读深度、事件映射、情绪价值、过度脑补、元素和灵数使用等维度进行结构化评分。**不做什么**：不让评审模型阻塞主生成，不把模型评分当成绝对真值。
- **为什么**：对应当前输出质量缺少外部评审、人工评测成本高且结果不稳定的问题。
- **怎么做**：主结果先展示；后台提交问题、牌阵、牌面、生成结果和评测标准；评审结果写入管理端质量记录；失败时记录“模型评审未完成”，支持重新评审。
- **做到什么程度**：主生成不因评审超时而失败；评审结果能保存为结构化 JSON；管理端能查看总分、维度分、风险提示和评审状态；评审成本和耗时可统计。

- **为什么**：对应当前输出标准没有量化、迭代记录分散在 AI 对话中、每次修改后难以比较效果的问题。
- **怎么做**：建立恋爱、事业、学业、人际关系、综合运势及重点牌阵样例；记录输入、prompt 版本、模型配置、输出、规则检查、人工评分和备注；与 prompt 变更同步推进。
- **做到什么程度**：每个 prompt 版本都有唯一编号；至少有一批可重复测试样例；同一案例可比较不同版本输出；评测表能记录问题相关性、位置对应、格式合规、总结有效性和建议可执行性。
- **优先级**：P1；前置依赖：第 7 节输出结构、第 9-11 节评测规则；与 P1-03、P1-04 并行推进，不等待异步模型评审。

- **怎么做**：先对 PDF、提示词规则、历史案例和客户数据分级；拆分主题、来源和适用范围；建立脱敏案例集；记录可检索字段；与 prompt 版本和离线评测并行。
- **做到什么程度**：形成资料目录、来源字段、隐私等级、适用场景和脱敏规则；至少有一批可人工检索的结构化资料；任何资料进入生成前都能追溯来源。

## 7. AI 输出内容结构审计

### 7.1 当前问题

当前产品已经具备 AI 解读能力，但 AI 输出质量主要依赖提示词约束和人工反馈微调，还没有形成独立的输出结构标准、质量评测表、自动检查机制和管理端质量记录。

输出内容结构不能只写成“开场、牌意、总结、建议”这种大模块。后续审计、PRD 和提示词系统必须保留产品负责人给出的原始模块和比例。比例总和不等于 不是问题，这些比例表达的是相对权重和结构约束，用于减少模型在内容组织上的漂移。

### 7.2 AI 输出内容结构骨架（公开版）

公开版本只展示结构设计思路，不公开 Prompt 的具体权重、完整模板、内部标记和逐条指令。产品将输出拆分为：问题理解、牌面观察、逐牌解读、牌间关系、事件映射、边界说明、建议与情绪回应等可验证模块，并通过版本化规则保证结构稳定。

### 7.3 技术边界与输出模块的对应关系（公开版）

- 输出必须围绕用户输入、牌阵和牌面上下文，不补写未经提供的事实。
- 每张牌需要与对应牌位关联，不能只输出通用牌义。
- 总结和建议需要回到用户问题，且不替用户做决定。
- 免责声明、表达边界和情绪回应属于必要质量约束。
- 具体 Prompt 模板、模块权重和测试样例属于内部方法资产，本公开版本不展开。

## 8. AI 质量评测方案

### 8.1 评测目标

AI 质量评测的目标不是让 To C 客人给专业性打分，而是在后台判断生成内容是否达到了产品预设的内容结构、专业细节、边界约束和用户问题回应要求。

默认原则：

- C 端客人看不到任何评分。
- 评审结果只进管理端的质量记录。
- 评审失败不影响主生成流程。
- 规则自动检查和模型评审分开实现。
- 用户反馈只用于体验反馈，不作为专业质量评审的唯一依据。

### 8.2 方案一：规则自动检查

实现方式：在本地代码或后端生成后处理逻辑中，对输出文本做规则检查，不需要新增模型 API 调用。

可检查项：

- 每张牌字数下限是否满足。
- 是否出现违禁词。
- 是否出现 Markdown 符号。
- 是否出现装饰性符号。
- 是否出现牌阵位置标题。
- 是否出现免责声明。
- 是否出现“替用户做决定”的表达。
- 是否出现“问题为空”“你还没想清楚”等禁止表达。
- 是否按牌阵位置覆盖每张牌。

成本：

- API 成本：0。
- 开发成本：中等，需要写规则检测函数和质量记录结构。
- 准确性：适合检查格式、字数、违禁词和必备模块，不适合判断内容深度。

是否新增评审 API 调用：

- 否。

串行还是异步：

- 可在生成结束后立即本地执行，耗时极短。

界面呈现：

- C 端不展示。
- 管理端新增“质量记录”或“本次生成检查结果”区域，显示通过项、风险项、失败项。

失败或超时降级：

- 本地规则检查基本不存在 API 超时问题。
- 如果规则检查异常，只记录“规则检查失败”，不影响用户查看输出。

适用阶段：

- 建议作为 P0 或 P1 的第一阶段评测能力。

### 8.3 方案二：异步模型评审

实现方式：主生成完成后，用户先看到输出；系统在后台把“用户问题、牌阵、牌面、生成结果、评测标准”发送给另一个模型，让模型按评分表输出结构化 JSON。

可评审项：

- 问题相关性。
- 解读深度。
- 事件映射质量。
- 情绪价值是否合适。
- 是否存在过度脑补。
- 是否存在逻辑断裂。
- 元素、灵数、人物、画面、关系动力是否被充分使用。

成本：

- API 成本：每次生成后新增一次评审调用。
- 评审成本：与输入长度、模型和调用频率有关，内部计费估算不在公开版本展示。
- 对整体 API 成本影响：如果每次生成都评审，成本大约接近“主生成之外再增加一次中等长度模型调用”。实际费用取决于所用模型单价，应按供应商后台价格计算。
- 成本状态：公开版本只保留方案判断，不公开内部价格和调用量测算。
- 开发成本：中高，需要新增评审接口、结构化输出解析、存储和管理端展示。

是否新增评审 API 调用：

- 是。

串行还是异步：

- 推荐异步，不推荐串行。
- 串行会让用户等待变长。
- 异步可以让用户先读结果，后台再完成质量记录。

界面呈现：

- C 端不展示。
- 管理端新增“AI 输出质量记录”。
- 每条历史记录可显示：规则检查结果、模型评审总分、维度得分、风险提示、建议修正方向。

失败或超时降级：

- 评审失败不影响主生成。
- 记录为“模型评审未完成”。
- 可提供“重新评审”按钮。

适用阶段：

- 建议作为 P1 功能，不建议在 P0 UI 改版前实现。

### 8.4 方案三：离线批量评测

实现方式：先不在用户每次生成后自动评审，而是建立一批测试问题、牌阵和牌面样例，定期批量生成并评测。

适用样例：

- 恋爱问题。
- 事业问题。
- 学业问题。
- 人际关系问题。
- 综合运势问题。
- 万能牌阵。
- 时间流运势牌阵。
- 维纳斯爱之牌阵。
- 双抉择牌阵。
- 二选一牌阵。

成本：

- API 成本：可控，因为只对样例集评测，不对所有用户生成评测。
- 开发成本：中等，可以先用表格和脚本半自动完成。
- 运营成本：需要人工维护样例和定期复盘。

是否新增评审 API 调用：

- 是，但不是每次用户生成都调用。

串行还是异步：

- 离线执行，不影响用户体验。

界面呈现：

- 不进入 C 端。
- 可先用表格记录，后续再进入管理端数据看板。

失败或超时降级：

- 不影响主产品。
- 失败样例单独记录，后续重跑。

适用阶段：

- 建议作为 P0/P1 之间的过渡方案。先用它建立评测标准，再决定是否做实时异步模型评审。

### 8.5 推荐方案

推荐先做“方案一 + 方案三”，暂不立即做“方案二”。

原因：

- 当前最急的是补齐 UI、新手引导和输出质量标准。
- 规则自动检查成本低，能快速发现格式、字数、违禁词、免责声明等硬性问题。
- 离线批量评测适合建立样例集和评测表，帮助你先理解“什么是好输出”。
- 异步模型评审更完整，但会增加接口、存储、后台展示和成本，适合后续管理端升级时再做。

## 11. 评分表维度细化

### 11.1 问题相关性

1 分：几乎没有回应用户原始问题，只是在泛泛解释牌义。

3 分：回应了问题类型，但和用户具体事件绑定不够。

5 分：始终围绕用户原始问题展开，牌意、总结和建议都能回到事件本身。

### 11.2 牌阵位置对应

1 分：没有使用牌阵位置，或位置和牌意混乱。

3 分：提到部分位置，但没有稳定对应每张牌。

5 分：每张牌都与对应牌阵位置建立清晰关系。

### 11.3 逐张牌解读完整度

1 分：只给出通用牌义，缺少细节。

3 分：有部分牌面解释，但维度不完整。

5 分：逐张牌解读覆盖四元素、背景故事、人物、视线方向与姿态、画面意象、隐喻、时间顺序、灵数变化及对比、画面细节、关系动力、情景。

### 11.4 元素解读

1 分：没有分析元素，或只报出元素名称。

3 分：能识别部分元素，但缺少互动和流动分析。

5 分：能识别四元素的缺失、复现、叠加；能分析元素间互动（黄金黎明体系：风火相互增强、水火相互抑制）；能判断元素流动方向。

### 11.5 灵数变化解读

1 分：没有灵数分析。

3 分：提到单张牌灵数，但缺少牌间对比。

5 分：能识别灵数的上升、下降、跳跃、波动，并做牌间灵数对比。

### 11.6 画面和人物分析

1 分：没有画面细节，只讲抽象结论。

3 分：有画面描述，但与用户事件连接不足。

5 分：能结合人物、背景、画面、隐喻、人物的视线方向和姿态、意象、画面细节，把牌面转译到用户情景中。

### 11.7 牌与牌交互关系

1 分：三张牌彼此孤立。

3 分：有简单总结，但关系动力不清楚。

5 分：能分析总体趋势、情景、元素的流动方向、互动方式、缺失、复现、灵数的波动上升或者下降或者跳跃。

### 11.8 事件映射

1 分：只讲牌，不讲用户问题。

3 分：偶尔回到用户问题，但映射较浅。

5 分：总结后对事件本身和问题的映射及解读充分，能让用户感到内容围绕自己的问题展开。

### 11.9 免责声明和边界

1 分：没有边界提示，或直接替用户做决定。

3 分：有边界提示，但表达生硬或位置不稳定。

5 分：自然表达“不会帮你做决定只给你展示问题的结果走向”，并且全文不替用户做决定。

### 11.10 建议质量

1 分：建议空泛，或直接命令用户。

3 分：建议和问题有关，但可执行性一般。

5 分：建议来自牌面和事件映射，方向清楚，不替用户决定。

### 11.11 情绪价值

1 分：没有情绪回应，或只说空泛安慰。

3 分：有安慰，但和事件结合不深。

5 分：能还原事件本身后对客户进行肯定或安慰，并根据情景、问题和结果分配情绪价值。

### 11.12 格式合规

1 分：出现大量 Markdown、装饰符号、违禁词或格式混乱。

3 分：基本可读，但仍有少量格式问题。

5 分：无 Markdown 加粗、无装饰性分隔符、无违禁词、段落清楚、阅读顺畅。

## 12. RAG 现状与目标能力

### 12.1 当前现状判断

从当前项目和产品负责人描述看，项目曾经将两本书《其实你已经很塔罗了》和《塔罗葵花宝典》的 PDF 版本，以及历史聊天记录或咨询语料，作为知识来源输入给 AI 使用。这个过程具备“知识增强生成”的意图。

但当前不能直接把它表述为“已实现完整 RAG 系统”。原因是标准 RAG 通常至少包括：

- 文档清洗。
- 文档切分。
- embedding 向量化。
- 向量数据库。
- 检索。
- 召回。
- 重排。
- 上下文拼接。
- 生成。
- 评测。

当前版本可以稳妥表述为：

通过系统提示词、业务语料、历史咨询记录和塔罗知识文本，构建了面向塔罗咨询场景的上下文增强生成机制；后续目标是将两本塔罗书籍、历史案例和输出边界规则整理为可检索、可评测、可维护的 RAG 知识系统。

### 12.2 RAG 目标能力

完整 RAG 系统应服务三个目标：

1. 提升牌意准确性。

通过检索《其实你已经很塔罗了》和《塔罗葵花宝典》的相关段落，减少模型凭空发挥。

2. 提升输出风格稳定性。

通过检索历史优质案例，让模型参考已验证的话术结构和表达方式。

3. 提升边界控制能力。

通过检索禁止词、格式规则、免责声明规则和事实边界规则，减少越界输出。

### 12.3 RAG 建设建议

建议分阶段建设，不要一上来做复杂系统。

阶段一：资料结构化。

- 将两本 PDF 拆成章节。
- 标注每章主题。
- 提取牌义、元素、灵数、牌阵、禁忌表达。
- 先形成结构化表格。

阶段二：离线知识库。

- 把资料拆成小段。
- 每段记录来源、主题、适用牌、适用场景。
- 先不接入实时生成，只作为人工检查和提示词优化依据。

阶段三：检索增强生成。

- 用户选择牌阵和牌面后，系统检索相关牌义、元素、灵数和案例。
- 将检索结果拼接进生成上下文。
- 控制检索内容长度，避免上下文过长影响生成稳定性。

阶段四：RAG 评测。

- 检查检索内容是否相关。
- 检查生成内容是否正确使用检索内容。
- 检查是否出现引用错误或过度扩展。

- 在管理端打开一条生成记录 → 显示问题摘要、牌阵、牌面、prompt 版本、规则检查、人工评语和评测结果；验收人：我；验收方式：走查/数据。
- 修改一条质量记录并刷新管理端 → 修改内容仍然存在，且与原始会话保持关联；验收人：我；验收方式：走查/数据。
- 打开基础数据看板 → 可以看到访问、生成成功率、失败率、保存率、反馈率和牌阵分布；验收人：我；验收方式：走查/数据。
- 抽样对比看板指标和原始埋点 → 统计口径一致，能够解释差异；验收人：我；验收方式：数据。
- 运行同一测试案例的两个 prompt 版本 → 输出、规则检查和人工评分可以按版本比较；验收人：我；验收方式：评测表。
- 查看 RAG 资料目录 → 每条资料有来源、主题、适用场景、隐私等级和脱敏状态；验收人：我；验收方式：走查。
- 触发异步模型评审超时 → 主生成结果仍可查看，评审状态记录为未完成，支持后续重新评审；验收人：我；验收方式：走查/数据。

### 13.3 P2 商业化验收边界

- 在未达到流量和用户反馈前检查支付需求 → 系统不出现正式支付入口，不创建无必要的订单和会员数据；验收人：我；验收方式：走查。
- 查看商业化可行性预研记录 → 记录支付、账号、权益、售后、退款、合规和获客前置条件，并明确暂不开发；验收人：我；验收方式：走查。

## 14. 当前主要问题归纳

### 14.1 产品问题

- 没有正式产品文档。
- 没有 PRD。
- 没有验收标准。
- 用户流程已经被产品负责人梳理，但还没有沉淀到正式文档。
- AI 输出结构有清晰想法，但还没有写成标准化要求。
- 迭代记录分散在 AI 对话和个人反馈中。

### 14.2 体验问题

- 新手引导不足。
- UI 视觉不够高级。
- 界面缺少明显亮点。
- 第一次使用的客户不一定理解如何提问、如何选牌阵、如何理解结果。
- 历史浏览是全局入口，但界面上需要更清楚表达。

### 14.3 AI 问题

- Claude 接口时期容易触发身份设定和边界问题。
- 换成 DS 后接口问题基本规避，但输出质量仍需要评测机制。
- 当前反馈微调只作用于当次结果，不等于进入长期知识库。
- RAG 是目标能力，但当前是否完整实现仍需核查。
- 输出质量缺少规则自动检查和模型评审记录。

### 14.4 数据问题

- 访客端历史依赖浏览器本地缓存，用户清缓存或换设备后可能丢失。
- 管理端数据维护依赖导入记录和导出记录。
- 更新迭代会影响管理端数据连续性。
- 数据库选择需要做，但不能牺牲隐私边界。

### 14.5 运营问题

- 没有流量监测。
- 没有数据看板。
- 不知道用户是否访问。
- 不知道用户在哪一步退出。
- 不知道生成失败率。
- 不知道保存到历史的比例。
- 管理端目前更像私人工作台，不是真正运营后台。

## 15. 优先级建议

### P0：按 A1-A10 完成核心使用流程和 UI 交互

P0 不再按提出顺序平铺，而是严格按用户从进入主界面到完成归档的顺序推进：

```text
A1 主界面和新手引导
A2 历史入口和返回
A3 问题输入和提问引导
A4 事件分类
A5 牌阵选择
A6 虚拟/实体牌和已选牌面
A7 抽牌过程侧操作
A8 生成前确认和必填判断
A9 生成状态、错误和重试
A10 解读阅读、反馈微调和归档
```

详细范围以第 6.1 节需求卡片为准。P0 开始前先做低保真页面结构，再进入视觉设计和代码改动。

### P1：按内部依赖推进数据、质量和管理能力

P1 的固定顺序为：

```text
① 数据库方案选择
② 基础埋点
③ 规则自动检查
④ 管理端质量记录测试模块 v1
⑤ 基础数据看板 v1
⑥ 异步模型评审
```

离线批量评测与 prompt 版本管理同步推进，不等待异步模型评审；RAG 资料结构化与 P1 主链路并行推进，但必须先完成资料来源、隐私等级和脱敏边界确认。

### P2：支付功能和商业化

P2 继续保留支付接口、账号体系、订单记录、会员权益、付费内容限制、售后退款、获客渠道和转化路径，但当前仅保留为后置规划。没有稳定流量和获客渠道时，不进入正式支付开发。
